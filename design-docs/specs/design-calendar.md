# Calendar and CalDAV Design

mailcal gains the calendar half of its name: user-owned calendars with
events (recurrence, all-day and timed, time zones), mentions by mail
address, R2-backed attachments, URL links, and CalDAV client sync with
iCloud. Everything is exposed through the existing `/graphql` endpoint so
agents and the SolidJS client share one API.

Explicitly out of scope (by request and by design):

- Attendee RSVP / attendance management. No accept/decline/tentative state
  exists anywhere: not in the domain, not in D1, not in GraphQL, not in the
  ICS mapping, not in the UI. `PARTSTAT`/`RSVP` parameters found in
  imported ICS are dropped.
- Acting as a CalDAV *server*. mailcal is a CalDAV *client* of iCloud
  (discovery, multiget, etag sync). No new hono protocol endpoints.
- VALARM/reminders, VTODO/VJOURNAL, calendar sharing between mailcal users
  (beyond mention visibility, below), FTS over events, scheduled background
  sync (sync is an on-demand mutation; a cron trigger is a later follow-up).

## Domain model

IDs (in `value-objects/ids.ts`, same brand + `createXxxId` pattern, always
caller-supplied): `CalendarId`, `CalendarEventId`, `EventLinkId`,
`CaldavAccountId`, `CaldavCalendarId`.

`TimeZoneId` (`value-objects/time-zone.ts`): branded string validated with
`Intl.DateTimeFormat` (constructing with an unknown zone throws); dual
constructors `parseTimeZoneId` (null) / `createTimeZoneId` (throws
`ValidationError`), mirroring `EmailAddress`.

`Calendar`: `{ id, ownerUserId, name (1..120), color (#rrggbb), description?,
createdAt, updatedAt }`. Hard-deleted; deleting a calendar cascades events.

`CalendarEvent`:

```
{
  id, calendarId,
  uid,                       // iCalendar UID; generated by application layer
  title (1..500), description?, location?,
  time: EventTime,
  recurrence?: RecurrenceRule,
  exdates: readonly OccurrenceStart[],   // excluded occurrence starts
  overrideOf?: { parentEventId, recurrenceInstanceStart },  // RECURRENCE-ID
  mentions: readonly EmailAddress[],     // no status of any kind
  links: readonly EventLink[],           // { id, url, title?, position }
  createdAt, updatedAt
}

EventTime =
  | { kind: "TIMED";   startsAt: UtcInstant; endsAt: UtcInstant; timeZone: TimeZoneId }
  | { kind: "ALL_DAY"; startDate: IsoDate;   endDateExclusive: IsoDate }
```

Invariants (smart constructor `createCalendarEvent`, throws
`ValidationError`): `endsAt > startsAt`; `endDateExclusive > startDate`;
override events carry no `recurrence`; an event is either a series master
(may have `recurrence`) or an override, never both; `links[].url` must be
absolute `http(s)`; mentions are normalized `EmailAddress`es, deduplicated.

`RecurrenceRule` (`value-objects/recurrence.ts`): supported RFC 5545 subset

```
{ freq: DAILY|WEEKLY|MONTHLY|YEARLY, interval >= 1,
  count? | until? (mutually exclusive),
  byDay?: Weekday[], byMonthDay?: (1..31)[], byMonth?: (1..12)[],
  weekStart?: Weekday (default MO) }
```

Dual constructors parse/serialize the RRULE text form
(`parseRecurrenceRule` / `formatRecurrenceRule`); unsupported parts
(`BYSETPOS`, `BYWEEKNO`, `BYHOUR`, `SECONDLY`, **negative `BYMONTHDAY`**...)
make `parse` return null (sync import then falls back, see CalDAV section).
Negative month days are deliberately outside the subset: "the last day of
the month" cannot be expressed by the day-of-month matcher expansion uses,
so admitting one would silently yield zero occurrences rather than the
intended day.

`expandOccurrences(event, rangeStartUtc, rangeEndUtc, limits)` is a pure
domain function: it walks occurrences by calendar arithmetic in the event's
time zone (timed) or in dates (all-day), applies `interval`, `byDay`,
`byMonthDay`, `byMonth`, honors `count`/`until`, removes `exdates`, and
converts each local start to UTC via an `Intl`-based offset lookup.
Nonexistent local times (spring-forward gap) shift forward by the gap;
ambiguous times (fall-back) take the earlier offset. `COUNT` is consumed by
generated occurrences before `EXDATE` filtering (an EXDATE does not extend
the series). Hard caps: expansion range <= 400 days and <= 1000 occurrences
per event per query — exceeding the range is `ValidationError`; the
occurrence cap truncates and is surfaced in the result.

`CaldavAccount`: `{ id, userId, serverUrl, username, passwordCiphertext,
principalUrl?, homeSetUrl?, createdAt, updatedAt }`. The app-specific
password exists in plaintext only transiently inside the sync/connect use
cases; the domain entity holds ciphertext only.

Capabilities: `ApiKeyCapability` gains `CALENDAR_READ` and
`CALENDAR_WRITE` (non-hierarchical, like the existing six).

## Authorization

Single choke point stays `policies/authorization.ts`.

- USER viewers: a calendar and its events are readable/writable by the
  owner. `ADMIN` role reads/writes all calendars (parity with mail admin
  surface). `VIEWER` role may read own calendars only (`VIEWER` cannot hold
  write; extends the existing "VIEWER may only hold MAIL_READ and
  FILE_LINK" rule to also permit `CALENDAR_READ`).
- Per-user calendar rules (`UserCalendarPermission`, migration `0008`):
  admin-assigned ALLOW/DENY rules mirroring `user_mail_permissions`. A rule
  names `{ capability: CALENDAR_READ|CALENDAR_WRITE, effect, ownerUserId }`
  where `ownerUserId` is the *calendar owner* the rule applies to (`null` =
  every owner, the viewer's own included) — owner is the same axis API-key
  scopes match on. Evaluation layers on top of the role baseline: DENY beats
  everything (including ADMIN default access and ownership), ALLOW extends
  access to another owner's calendars, and the role ceiling still applies
  (a VIEWER can never be ALLOWed `CALENDAR_WRITE`). Rules are loaded onto
  the USER viewer as `calendarPermissions` alongside the existing mail
  `permissions`, and managed by ADMINs via
  `addUserCalendarPermission` / `removeUserCalendarPermission` (same shape
  as `addUserMailPermission` / `removeUserMailPermission`).
- Mention visibility: a USER whose account email is mentioned on an event
  can read that event (and it appears in `eventsMentioningMe`), read-only.
  Mentions never grant calendar-level or write access.
- API_KEY viewers: calendar scopes reuse the existing scope row shape
  (capability + domain + `AddressPattern`), matched against the **calendar
  owner's account email** — exactly the mechanism mail scopes use against
  mailbox addresses. `CALENDAR_WRITE` scoped to `taco@example.com` can edit
  calendars owned by that user; pattern `*` spans all owners. Keys inherit
  nothing from their creating user (unchanged doctrine).
- Probe resistance is preserved: unauthorized calendar/event reads surface
  `NOT_FOUND`, never `FORBIDDEN` (same asymmetry as mail,
  `application/src/errors.ts`).
- CalDAV accounts are strictly per-user (`userId`); API keys cannot manage
  CalDAV accounts (`connectCaldavAccount` requires a USER viewer — an agent
  should not be able to exfiltrate or rotate iCloud credentials), but a
  suitably scoped key may trigger `syncCalendar`.

## D1 schema (migration `0006_calendar.sql`)

Rules honored: no semicolons inside literals, no triggers (runner splitter),
CHECK widening via the 0005 `_new` + rename pattern.

- Rebuild `api_key_scopes` with capability CHECK widened to 8 values.
- `calendars(id PK, owner_user_id -> users CASCADE, name, color,
  description, created_at, updated_at)`; index on `owner_user_id`.
- `calendar_events(id PK, calendar_id -> calendars CASCADE, uid,
  all_day INTEGER, starts_at INTEGER, ends_at INTEGER, time_zone TEXT,
  start_date TEXT, end_date_exclusive TEXT,
  range_start_utc INTEGER, range_end_utc INTEGER,   -- always populated
  rrule TEXT, exdates_json TEXT, recurrence_until_utc INTEGER,
  override_of_event_id -> calendar_events CASCADE,
  recurrence_instance_start INTEGER/TEXT,
  title, description, location, created_at, updated_at,
  CHECK timed/all-day column sets are exclusive)`;
  `UNIQUE(calendar_id, uid, recurrence_instance_start)`; index
  `(calendar_id, range_start_utc)`.
  `range_*_utc` are denormalized query columns: for non-recurring events
  the UTC bounds; for recurring masters the first occurrence start and
  `recurrence_until_utc` (null = unbounded) bound candidate selection.
- `event_mentions(event_id CASCADE, address, created_at,
  PK(event_id, address))`; index on `address`.
- `event_links(id PK, event_id CASCADE, url, title, position)`.
- `event_attachments(event_id CASCADE, attachment_id -> attachments,
  position, PK(event_id, attachment_id))`. The `attachments` table is
  untouched; an event claims a staged upload (`message_id IS NULL`) via
  this join table, reusing `POST /api/attachments` and the `att/...` R2
  layout unchanged.
- `caldav_accounts(id PK, user_id -> users CASCADE, server_url, username,
  password_ciphertext, principal_url, home_set_url, created_at,
  updated_at)`.
- `caldav_calendars(id PK, account_id CASCADE, calendar_id UNIQUE ->
  calendars CASCADE, remote_url, ctag, sync_token, last_synced_at)`.
- `caldav_event_states(event_id PK -> calendar_events CASCADE,
  caldav_calendar_id CASCADE, href, etag, last_synced_at)`.
- `caldav_deletions(caldav_calendar_id CASCADE, href, etag, deleted_at,
  PK(caldav_calendar_id, href))` — tombstones written when a synced local
  event is deleted, so the deletion can be pushed (`DELETE` + `If-Match`)
  on next sync despite the CASCADE removing `caldav_event_states`.

Multi-row event writes (event + mentions + links) use `SqlDatabase.batch`
(D1 batches are atomic); D1 has no interactive transactions, so all writes
are single-batch and idempotent by primary key.

Migration `0008_user_calendar_permissions.sql` adds
`user_calendar_permissions(id PK, user_id -> users CASCADE, capability
CHECK in (CALENDAR_READ, CALENDAR_WRITE), effect CHECK in (ALLOW, DENY),
owner_user_id -> users CASCADE NULL = all owners, created_by_user_id,
created_at)` with a unique rule index on
`(user_id, capability, ifnull(owner_user_id, ''))` so a duplicate
all-owners rule cannot stack, plus lookup indexes on `(user_id,
capability)` and `owner_user_id`. It depends only on `users`, so it is
independent of the 0006 calendar tables.

## GraphQL surface (SDL module `schema-calendar.graphql.ts`)

Types: `Calendar`, `CalendarEvent` (master/override, recurrence fields,
`mentions: [EmailAddress!]!`, `links: [EventLink!]!`,
`attachments: [Attachment!]!`), `EventOccurrence { event, occurrenceStart,
occurrenceEnd, isOverride }`, `EventLink`, `RecurrenceRuleInput/Type`,
`CaldavAccount` (never exposes ciphertext or plaintext), `CaldavCalendar`,
`CaldavDiscoveredCalendar`, `SyncCalendarResult { pulled, pushed, deleted,
conflictsResolvedRemoteWins, truncated }`.

Queries: `calendars`, `calendar(id)`, `calendarEvents(input:
{ calendarIds?, rangeStart!, rangeEnd!, expand: Boolean = true })` ->
`[EventOccurrence!]!` (expansion server-side so agents and web share it),
`calendarEvent(id)`, `eventsMentioning(address: String!, rangeStart,
rangeEnd)` (USER: only own addresses unless ADMIN; API key: address must
match a `CALENDAR_READ` scope pattern), `caldavAccounts`. The admin user
management surface gains `calendarPermissions:
[UserCalendarPermission!]!` on `User` (mirroring the mail
`permissions` field).

Mutations: `createCalendar` / `updateCalendar` / `deleteCalendar`;
`createCalendarEvent` / `updateCalendarEvent(editScope:
THIS_OCCURRENCE | ENTIRE_SERIES)` / `deleteCalendarEvent(editScope)` —
`THIS_OCCURRENCE` on a master creates/updates an override row (update) or
appends an EXDATE (delete); `addEventMention` / `removeEventMention`
(mention management addressed by mail address per acceptance criteria;
create/update inputs also accept full `mentions`/`links` arrays);
`addEventLink` / `removeEventLink`; `attachFileToEvent(eventId,
attachmentId)` / `detachFileFromEvent`;
`addUserCalendarPermission(userId, input)` /
`removeUserCalendarPermission(id)` (ADMIN only, mirroring the mail
permission mutations); `connectCaldavAccount(serverUrl,
username, appPassword)` -> discovered calendars; `linkCaldavCalendar
(accountId, remoteUrl, mode: IMPORT_NEW | BIND_EXISTING(calendarId))`;
`syncCalendar(calendarId)`; `deleteCaldavAccount`.

Errors reuse the six existing `extensions.code` values;
`connectCaldavAccount`/`syncCalendar` map network/auth failures to
`SERVICE_UNAVAILABLE` (server unreachable / 5xx) and `BAD_USER_INPUT`
(401 from iCloud = bad app-specific password). When
`MAILCAL_CREDENTIAL_KEY` is unset, CalDAV mutations fail with
`SERVICE_UNAVAILABLE` and a clear message (the
`createUnavailableMailSender` precedent); the rest of the calendar feature
works without the secret.

Resolvers live in `resolvers/calendar-query.ts` / `calendar-mutation.ts` /
`calendar-types.ts`, call `ctx.usecases.*` only, and are merged in
`buildGraphQLSchema` alongside the existing maps.

## ICS mapping (adapter `ics/ics-codec.ts`, behind application `IcsCodec` port)

RFC 5545 subset, mirroring the `MimeParser`/`MimeBuilder` port precedent.

Serialize (`VCALENDAR`/`VEVENT`): `UID`, `DTSTAMP`, `SUMMARY`,
`DESCRIPTION`, `LOCATION`, `DTSTART`/`DTEND` (`TZID=` for timed,
`VALUE=DATE` for all-day), `RRULE`, `EXDATE`, `RECURRENCE-ID` (overrides),
`URL` (first link) plus `X-MAILCAL-LINK;X-TITLE=...:<url>` for every link,
`X-MAILCAL-MENTION:mailto:<address>` for every mention. Mentions are
deliberately **not** written as `ATTENDEE`: ATTENDEE implies iTIP
scheduling — iCloud would email invitations and attach PARTSTAT semantics,
both forbidden here. Line folding at 75 octets, CRLF, RFC 6868/5545
escaping. IANA TZIDs are emitted without VTIMEZONE blocks (accepted by
iCloud/Google; documented residual risk for strict servers).

Parse: tolerant unfold; map `ATTENDEE` -> mention (dropping `PARTSTAT`,
`RSVP`, `ROLE`, `CN` — address only), `X-MAILCAL-MENTION` -> mention,
`URL`/`X-MAILCAL-LINK` -> links, `EXDATE` (multi-value, TZID-aware),
`RECURRENCE-ID` -> override linkage by `(uid, instance start)`. Unknown
TZIDs fall back to UTC with a per-event warning in the sync result;
unparsable `RRULE` (unsupported subset) imports the master as a
non-recurring event flagged `recurrenceUnsupported` in the sync result and
is excluded from push (never overwrite a remote event we cannot represent).
Unknown properties are not preserved: push is a full re-serialization, so
foreign props (e.g. `VALARM`) are lost on events mailcal edits — documented
limitation, listed in risks.

## CalDAV client (adapter `caldav/caldav-client.ts`, behind `CaldavClient` port)

fetch-based, Basic auth (username + app-specific password), no third-party
dependency; a minimal namespace-tolerant XML reader for `multistatus`
responses lives beside it (tested against iCloud-shaped fixtures).

- Discovery: `PROPFIND` `current-user-principal` on
  `https://caldav.icloud.com/.well-known/caldav` (following redirects,
  including cross-host `pXX-caldav.icloud.com`), then
  `calendar-home-set`, then `Depth: 1` `PROPFIND` for calendars
  (`resourcetype`, `supported-calendar-component-set` containing VEVENT,
  `displayname`, `getctag`, `sync-token`).
- Incremental sync: `sync-collection` REPORT (RFC 6578) with the stored
  `sync-token`; on `507`/invalid-token or absent support, fall back to
  `Depth: 1` `PROPFIND` etag listing diffed against `caldav_event_states`.
  Changed hrefs are fetched via `calendar-multiget` REPORT (chunked).
- Push: `PUT` with `If-Match: <etag>` (update) / `If-None-Match: *`
  (create), `DELETE` with `If-Match`. `412 Precondition Failed` marks a
  conflict, resolved below; the push set is `caldav_event_states` rows
  whose event `updated_at > last_synced_at`, plus `caldav_deletions`.

Sync algorithm (`syncCalendar` use case): pull remote changes -> upsert
locally -> push local dirty -> push tombstones -> store new
ctag/sync-token/etags. Conflict policy is deterministic **remote wins**:
if both sides changed since `last_synced_at` (or a PUT returns 412), the
remote version replaces local and the count is reported in
`SyncCalendarResult.conflictsResolvedRemoteWins`. Remote deletion deletes
local; local deletion of a synced event writes a tombstone. Each pulled
event maps by `UID` (+ `RECURRENCE-ID`); UID collisions across calendars
are scoped per calendar by the unique index.

## Credentials

`CredentialCipher` port; adapter implementation uses WebCrypto AES-256-GCM.
Key material: `MAILCAL_CREDENTIAL_KEY`, a base64-encoded 32-byte secret set
with `wrangler secret put` (run through `kinko exec`); `config.ts` fails
fast on set-but-invalid values (the `resolvePublicOrigin` pattern) and
resolves to "unavailable" when unset. Ciphertext format:
`v1:` + base64(12-byte random IV || ciphertext+tag). Plaintext passwords
never appear in GraphQL responses, logs, or D1; only ciphertext is stored.
Local dev without the secret simply has CalDAV disabled.

## Data flow summaries

- Create event: dialog -> `createCalendarEvent` mutation -> resolver ->
  use case (authz -> domain factory validates -> repo single `batch`
  insert of event+mentions+links) -> occurrence cache invalidated for the
  visible range. If the calendar is CalDAV-linked the event becomes dirty
  (its `updated_at` exceeds `last_synced_at`) and is pushed on next sync —
  mutations never perform network I/O.
- Range listing: `calendarEvents` -> repo candidate query (non-recurring
  overlap OR recurring window overlap via `range_start_utc` /
  `recurrence_until_utc`) -> domain expansion + override substitution +
  EXDATE removal -> occurrences sorted by start.
- Mention query: `eventsMentioning` -> authz (own address / scope match) ->
  index scan on `event_mentions.address` -> optional range expansion.
- Sync: see CalDAV section; runs inside the mutation request (bounded by
  multiget chunking and the occurrence caps), returns
  `SyncCalendarResult`.
- Attachment download: `GET /api/attachments/:id` authorization gains an
  event branch: attachment claimed by an event -> viewer must be able to
  read that event (owner/admin/mentioned/scoped key). File links gain the
  same branch on the *mint* and *revoke* sides: an event attachment carries
  no `messageId`, so `createAttachmentLink` authorizes through a claiming
  event the viewer can read, plus `FILE_LINK`. Because there is no address
  to scope it against, `FILE_LINK` is required at its coarsest form (held on
  any scope; a user viewer holds it unconditionally). An attachment no event
  has claimed stays unlinkable -- it is a staged upload belonging to
  nothing. Resolution of an already-minted token is unchanged: the token is
  the credential and never consults a viewer.

## Test strategy

- domain: recurrence expansion table-driven tests (DAILY/WEEKLY/MONTHLY/
  YEARLY, INTERVAL, COUNT vs EXDATE interplay, UNTIL, BYDAY incl. `-1SU`
  style negatives excluded from subset, DST spring-forward and fall-back
  fixtures in `America/New_York` and `Asia/Tokyo`, all-day multi-day),
  `EventTime` invariants, `TimeZoneId` validation, RRULE parse/format
  round-trip.
- adapter: ICS round-trip fixtures (own output, iCloud-shaped input with
  ATTENDEE/PARTSTAT to verify dropping, folded lines, EXDATE lists,
  VALUE=DATE); CalDAV client against canned multistatus XML fixtures
  (discovery redirect chain, sync-collection, fallback etag diff,
  multiget, 412 conflict); credential cipher round-trip + tamper
  rejection; repository real-SQL tests (candidate range query, batch
  atomicity, mention index, cascade behavior, tombstones) via existing
  `repositories/test-support.ts`.
- application: use cases over new in-memory fakes (calendar-repository
  fake honoring the authz-relevant shapes) — authorization matrix (owner /
  ADMIN / VIEWER / mentioned user / `CALENDAR_*`-scoped key / mail-only
  key gets NOT_FOUND / per-user ALLOW extends and DENY revokes including
  against ADMIN and ownership), editScope semantics, sync conflict policy
  against a scripted fake `CaldavClient`.
- infrastructure: `schema.test.ts`-style operation tests for the new
  module; attachment route event-authorization tests.
- web: `lib/calendar-dates` and calendar-store unit tests; `vite build`
  must pass.
- Gates: `bun run typecheck`, `biome check . --diagnostic-level=warn`,
  `vitest run && bun run --cwd apps/web test`; the pre-existing suite
  (1272 root + 151 web tests at design time) stays green; no touched file
  reaches 1000 lines.

## Rollout

Migrations 0006 and 0008 apply via the existing local runner and
`wrangler d1 migrations apply mailcal-db --remote`; they only add tables
and rebuild `api_key_scopes` (existing scope rows are copied verbatim —
mail keys are unaffected; the rebuild has a dedicated losslessness test).
The feature is additive; without `MAILCAL_CREDENTIAL_KEY` everything
except CalDAV works. No changes to ingest/send paths.
